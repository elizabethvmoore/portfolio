The membership and giving engine

How I built Whatcom Museum's online membership and donation system from scratch, and made it reliable enough to trust with real money.

Role
Sole developer
Timeline
Summer 2026, shipped September
Stack
WordPress, PHP, JavaScript
Integrations
Stripe Checkout, MonkeyPod CRM

The problem

The museum sells 12 membership levels and takes donations online, but every purchase had to end up in MonkeyPod, the CRM where staff manage members, donors, receipts, and accounting. Anything that didn't land there correctly meant manual cleanup, missed renewals, or books that didn't match the bank.

I needed a system where a member pays once and everything else happens on its own: the contact, the membership, the donation records, the receipt, and the email signups, all booked correctly the first time.

The catch: there was no test environment. MonkeyPod has no sandbox, so every API call writes to the live database. Every design decision had to assume that a mistake would create real records for real people.

How it works

The system connects four pieces. The most important design choice is the one in the middle: the browser never talks to Stripe or MonkeyPod directly.

Member's browser

Membership and donation forms, and the success page after payment

→

Secure PHP proxy

Holds the API keys, only forwards an approved list of calls, and logs every one

→

Stripe Checkout

Takes the payment, then sends the member back to the success page

MonkeyPod CRM

Contacts, memberships, donations, receipts, and email lists

Keeping the keys on the server means no one can lift them from the page source, and the approved-calls list means the proxy can't be used to do anything the forms don't need.

A purchase, step by step

Before payment

  1. The member fills out a form for their level.
  2. The system checks MonkeyPod for an existing contact by email, so returning members aren't duplicated.
  3. If that lookup fails, it retries once, then stops with a clear try-again message, because nothing has been charged yet.
  4. The proxy opens a Stripe Checkout session with everything the CRM will need attached.

After payment

  1. The success page checks whether this purchase was already booked.
  2. It waits briefly for Stripe to report the exact processing fee.
  3. It books the membership donation first, the one record that must not be lost.
  4. Then it books everything else in parallel: receipts, the purchase interaction, and email signups.

Hard problems I solved

Returning members were being duplicated

Symptom
Every returning member got a brand-new contact record instead of matching their existing one.
Cause
A standard WordPress sanitizing function was silently mangling the @ in email addresses, so every lookup came back empty.
Fix
I sent the email as its own field and encoded it safely on the server. I also made the system treat a failed lookup as an error, never as "no match found."

Ghost purchases: paid, but never booked

Symptom
A few members paid successfully, but their records never appeared in the CRM.
Cause
I built an activity log for every API call, and it showed the bookings stopping partway through. Members were closing the tab before the success page finished its work.
Fix
I restructured the page to wait on only the one critical record and run everything else at the same time, shrinking the window from many sequential calls to one. I also wrote a step-by-step repair procedure for staff.

Renewals were stacking up instead of extending

Symptom
Online renewals created duplicate membership records and reset each member's "Member since" date.
Cause
Creating memberships directly through the API bypassed MonkeyPod's own renewal logic, and the documentation didn't explain how to trigger it.
Fix
I compared the data MonkeyPod's own store sends against mine and found an undocumented field that triggers its renewal workflow. I mapped all 12 levels to it and rebuilt the flow, so memberships now extend by a year and keep their history. This was the project's biggest goal.

Making the books match to the penny

Symptom
Website transactions didn't line up cleanly with Stripe payouts and the bank.
Cause
Records were missing the payment reference and the actual processing fee, which Stripe only reports a few seconds after the charge.
Fix
Working with the museum's finance team, I rebuilt how every transaction books: the right accounts and class, the Stripe reference on every record, and the real fee captured by briefly polling Stripe after checkout. Finance signed off on the new setup.

Built to fail safely

With no test environment and every write happening in the member's browser, each of these patterns exists because of a real failure it prevents.

PatternWhat it doesWhat it prevents
Match-first lookupFinds an existing contact before creating oneDuplicate member records
Fail loud earlyRetries once, then stops before paymentA glitch creating a bad record
Idempotency keysGives every write a unique key tied to the checkoutDouble-booked donations on refresh
Replay guardMarks a purchase done only after a clean runRe-running finished bookings, while letting interrupted ones retry
Critical-first bookingSaves the one essential record, then the rest in parallelGhost purchases from closed tabs
Activity logRecords every API call in WordPressProblems no one can diagnose
